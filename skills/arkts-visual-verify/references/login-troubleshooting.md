> **iOS 源输入**：读取 Swift/Objective-C、SwiftUI/UIKit、Xcode 工程及原生资源；实际源构建与设备观测依赖可用的源平台环境。鸿蒙侧构建和验收保持原流程。源侧操作详见 `a2h-spec/references/native-input.md`。

# 登录链排障方法论（A2H 迁移 · 认证 / 会话 / 签名 / 登录态刷新）

> **何时读**：Phase 4 scenario 建登录态失败（`NEED_APP_FIX`、接口 HTTP 200 但业务 `status` 非 0），
> 或登录"协议通了"但界面/持久化不对。**先读本文再动代码**——本文每一条都来自一次真实 A2H 项目上
> 两端明文抓包 / 主机侧直连逐字节对照，不是推测。
>
> **本文只放跨项目成立的方法与判据**。具体项目的 wire 真值（后端域名、签名 key、字段真值表、改动清单）
> 属于项目实录，放在被测项目 `spec/scenarios/LOGIN_KNOWLEDGE.md`（有则**同时**读）。
> 文中 `> 示例` 块是一个真实项目的实测值，用来说明"长什么样"，**不要照抄到别的项目**。

## 0. 三十秒分诊表（症状 → 缺陷类 → 第一探针）

| 症状 | 缺陷类 | 第一探针（不是第一修法） |
|---|---|---|
| 请求 HTTP 200，业务 `status` = 权限/签名类拒绝（如 -401） | ① 请求头**名**发错（常量名/值混淆）② 设备时钟漂 ③ 签名输入串与实际发送体不一致 | **先量时钟**（§3），再抓两端原文 diff 请求头**名**（§2） |
| 发码 / 绑定 / 拉档案一路"用户未登录"（如 -1001） | 上游 initUser 没建成会话，下游全部级联 | 只修上游；下游会自动消失，别一个个补 |
| **昨天还好的代码今天全链拒绝** | 设备时钟漂（模拟器休眠后必漂） | `hdc shell date +%s` 减宿主时间（§3）。**不要翻代码** |
| 登录成功（`status=0`、toast 登录成功）但页面仍显示未登录 | 鸿蒙侧页面刷新机制缺陷：iOS `onResume` 无对位钩子 | dump 一次布局，看登录页在栈顶时目标页节点是否仍在同一棵树（§6） |
| 退出登录后**冷启**又自动登录回去 | 登出只清内存、没清持久化 | 找 `clear()`：有没有连 Preferences / AppStorage 一起清（§7.1） |
| 已登录**冷启**昵称空白 / 闪一下登出态 | 冷启没从持久化种回运行时模型 | 看初始化只抄了 token/userId 还是连 userState/nickName 一起种（§7.2） |
| 已登录**冷启**变成游客态 | 迟到的失败应答无条件重建了会话 | 按时间戳排一次启动期请求/应答/持久化恢复的先后（§7.3） |
| **全链**业务 -500，文案是服务器框架级英文（如 `Missing request attribute 'platformInfo'`） | 协议身份常量自造：渠道/包名/baseType 这类"填充值"被迁移侧发明了新值，服务器拿它查表失败挂在**解析层**——错误文案在骂字段缺失，真凶是值不合法 | 对照组二分（§2.6）：同一请求，一组产物实际值、一组源端真值 |
| 全链签名/鉴权类拒绝，且工程存在「注入槽」（build-profile buildProfileFields / 按名资源 / configure 钩子 / Provider 接口） | **注入槽空值**：注入机械造好了但值是空串——签名头 `ss/ee` 用空钥匙算出必错。四代载体实录：资源名槽→包装函数→导出钩子→BuildProfile 空串，**每种静态防御杀死一个载体它就换下一个** | 第 0 步先 grep 注入槽实值（`grep -A4 SIGNING_KEY build-profile.json5` 类）——空串即根因，值去 `raw_apis.json` 取（iOS端常量机器抽取件；人读版「值不落 spec」措辞不作为值不存在的判据） |
| 换遍客户端可控字段，同一业务错**纹丝不动** | 后端身份供给缺失：服务器侧没为这个包身份配置映射行（媒体号/渠道表/设备注册），**客户端无解** | 止损（§1 铁律 8）：带探针证据登记 external-deferred，停止客户端修复 |

> 示例（真实项目实测）：-401 的根因是把iOS常量 `Param._t="tt"` / `Param._s="ss"` 的**名字** `'_t'/'_s'`
> 当成了 header 名发出；后端只认 `tt/ss` → 签名头根本没被读到。同一份修好的代码次日又全链 -401，
> 是模拟器时钟慢了 18.8 分钟。两个独立成因，症状完全一样。

**协议通 ≠ 登录好。** 第一轮往往只把"请求打得通"修好；"登录成功后界面真的变成已登录 + 冷启仍在"
是第二轮，验收必须看界面（§9）。

## 1. 方法论铁律（比任何结论都重要）

1. **先抓原文，不猜。** 两端各抓一次同一接口的**完整请求头 + 请求体 + 响应体**，逐字节 diff。
   - iOS：宿主机透明代理最省事。`adb shell settings put global http_proxy 10.0.2.2:<port>`，
     宿主起一个 ~50 行的记录代理；跑完 `settings put global http_proxy :0` 还原。
   - 鸿蒙：在网络层请求执行处临时 hilog 打头/体/响应。**hilog 单条 >~1KB 会整条丢，按 ~900 字节分段打。**
   - 这一步 10 分钟，能省掉 8 轮盲猜（实测数字）。
2. **响应体里给人看的错误文案（如 `toastMsg`）绝不脱敏。** 它是方向标："权限校验未通过"= 看签名/头名；
   "用户未登录"= 看上游会话。凭据安全靠**不把 token 值写进单据**来保证，不靠抹掉状态文案。
3. **自检工具不能复用被检对象的假设。** 用自己发出的 header 名去校验自己发的 header 名 = 同义反复，
   永远全绿。校验基准必须来自**另一端**（iOS wire / 后端文档 / 主机侧直连回包）。
   > 示例：某次修复写了 80 行"请求契约矩阵"自检 `header['_s']`——矩阵里检查的也是错的那个名字，报了 8 轮绿。
4. **成功信号看最便宜的那个。** 发码成功 → 按钮进倒计时；绑定成功 → 目标页出现登录态专属入口。
   别只盯 `status` 数字。
5. **走 app 真实 UI 流程验证**（装→隐私→引导→入口→登录页→填号→勾协议→发码→输码→登录），
   别用直连接口/脚本模拟当最终验收——直连会漏掉启动期的 config / firstStart 等前置（见 §2.4）。
6. **主机侧直连探针是最省时间的工具，先建它。** 见 §2.5。
7. **迁移时"额外加的自愈/兜底逻辑"要专门复查**（§7.3）。它们最容易在竞态里帮倒忙，
   而且因为"看起来更健壮"很难被怀疑。
8. **排查有终点：先分层，穷举可控项后止损。** 顺序永远是——
   ① **传输层第一刀（零侵入）**：先看设备网络栈日志（鸿蒙 `hilog` 里 NETSTACK 域的
   `RespCode / errCode / daddr`）。HTTP 200 + errCode 0 = 出网了、服务器答了，明文放行/DNS/
   签名被拒三大类怀疑**一次性排除**，问题必在业务信封——这 30 秒决定后面所有方向，
   比抓包和加日志都便宜，永远第一步做；
   ② 业务层用探针（§2.5）拿服务器的业务码和 `toastMsg` 说话——**app 弹的笼统文案
   （"网络问题"）是错误映射的末端，信息已丢失，不作为排查输入**；
   ③ 对照组二分（§2.6）定位决定性字段；
   ④ **穷举客户端可控字段的等价类后结果仍不变 → 判定后端供给问题，停**。这是能和
   "还没试对"区分开的机械判据：结论的形状是"等价类内结果恒同"，不是"我试了几次都失败"。
   带探针输出为证据登记 external-deferred（销案钥匙在后端侧），绝不让修复循环在
   客户端空转。**发现晚可以接受，归因错、止损晚不可接受。**

## 2. 协议逆向手册：从iOS wire 复原签名/会话协议

目标：在动鸿蒙一行代码之前，拿到一份**可复算**的协议描述。按下面顺序做，每步都有产物。

### 2.1 找请求头的**名字**，对照iOS常量类的**值**

iOS项目通常有一个常量类（`object Param { const val _t = "tt" }` 之类）。翻译到 ArkTS 时高发的缺陷是
**把常量名当常量值**写成字面量：`header['_t']`。编译零报错，运行时静默失败。

- 探针：`grep` 鸿蒙侧所有 header / 参数名字面量，逐个对照iOS常量类的**值**（不是名）。
- 更稳的修法：引用鸿蒙侧已翻译好的同名常量（通常翻译器早就把 `Ext.ets` 里的 `Param` 翻对了，只是没人用）。
- 交叉证据：后端响应头 `Access-Control-Allow-Headers` 常明列它认的头名。

### 2.2 找签名函数，抄下**精确的拼接顺序**与**每个输入的来源**

- iOS侧一般是 `Sign.kt` / `SignUtil` 一类：记下 `hash(拼接串)` 的算法、大小写、每段来源。
- **签名输入的 body 必须是实际发出的那个字符串**（注入 platformInfo / 排序之后的），不是业务对象原始 JSON。
- 注意序列化差异：iOS Gson 对嵌套对象**按键字母序**输出；ArkTS `JSON.stringify` 按插入序。
  如果后端按自身序列化重算签名，键序不同就对不上——需要显式排序。
- 签名里若嵌了**时间桶**（如 `MD5(floor(ts/1000/60)+token)`），意味着后端拿自己的时钟重算，
  客户端时钟偏出窗口就永远拒绝——这直接引出 §3。

> 示例：`ss = SHA1(body + tt + token + MD5(floor(tt/1000/60) + token) + key)`，40 位大写 hex。
> 容忍窗实测 ≈2 分钟（≤90s 过、≥120s 拒），与"分钟桶 ±1"吻合。

### 2.3 设备指纹字段：按iOS wire **形态**对齐，不是按鸿蒙 API 原样填

iOS侧 platformInfo 一类字段（`systemVersion` / `phoneBrand` / `phoneModel` / `iosId` …）后端可能拿来做身份闸。
鸿蒙 API 原值（如 `OpenHarmony-6.0.1.112`、marketName `emulator`）形态不同，且**在模拟器上会直接暴露
非iOS / 模拟器身份**。

- 做法：从iOS wire 抄一份**实测值形态**（数字版本号、品牌串、机型串、16 位 hex iosId…），
  鸿蒙侧用 helper 映射到同形态。
- 判断力：这类对齐**不一定是当前失败的根因**（示例项目里对齐后仍 -401，直到修了头名才通），
  但通常无害且在别的包上曾是必要条件——做了就保留，别反复拆装。

### 2.4 启动顺序是协议的一部分

后端常要求设备先"注册"（如 `/app/config`）才认后续的 `initUser`。跳过前置直接打业务接口会得到
**看似签名问题、其实是设备未注册**的错误（示例：`-500 "... mediaNo is null"`）。
按 app 真实启动顺序复现，别只打你关心的那一个接口。

### 2.5 主机侧直连探针（强烈建议第一步就建）

不必"改代码→编译→装机→点界面"绕一圈才能验一个协议假设。用 ~50 行 Python 在**宿主机**复算签名直连后端，
一次往返 <1 秒，可以随意扫描变量：时间戳偏移、字段序、UA、平台字段、启动顺序。

```python
# 骨架——KEY / BASE / 签名公式 / header 名 全部从 §2.1–2.2 逆向结果里填，别抄别的项目
import hashlib, json, time, urllib.request
md5  = lambda s: ''.join(f'{b:02X}' for b in hashlib.md5(s.encode()).digest())
sha1 = lambda s: ''.join(f'{b:02X}' for b in hashlib.sha1(s.encode()).digest())
def sign(body, ts, token): return sha1(body + str(ts) + token + md5(str(ts//1000//60) + token) + KEY)
def call(path, obj, token='', ts=None):
    body = json.dumps(obj, separators=(',',':'), ensure_ascii=False)   # 键序按 §2.2 结论处理
    ts = ts or int(time.time()*1000)
    req = urllib.request.Request(BASE+path, data=body.encode(), method='POST')
    for k, v in {'token': token, 'tt': str(ts), 'ss': sign(body, ts, token), 'ee': KEY,
                 'User-Agent': UA, 'Content-Type': 'application/json;charset=utf-8'}.items():
        req.add_header(k, v)
    return json.loads(urllib.request.urlopen(req, timeout=15).read())['data']
```

它能直接产出两样东西：**时钟容忍窗**（只挪 `ts` 扫描）和 **应答字段真值表**（§5）。

### 2.6 对照组二分法：产物值 vs 源端真值

服务器把请求拒在业务层、但错误文案说不清原因时（尤其框架级英文报错），**别逐个猜字段**——
用 §2.5 探针打同一接口两次：

- **A 组**：产物**实际发送**的全套值（照抄迁移产物的装配代码，包括它自造的部分）；
- **B 组**：源端（iOS）**真值**的全套值（渠道号、包名、baseType、版本号——从源工程的
  构建配置/渠道表里抄，如 `product.xml` / flavor 的 `defaultChannel`）。

A 败 B 成 → 问题在客户端发的值里，**逐字段二分**（每次只换一个字段）直到找到决定性字段。
经验上头号嫌疑是**协议身份常量**：渠道/包名/baseType/operators 这类"看起来是无害填充"的字段，
迁移侧常给它们发明平台化新值（如 `channel='harmonyos'`）——但服务器拿它们**查表**，
查不到就在解析层拒绝，且错误文案往往指向别处（骂"字段缺失"，真凶是"值不在表里"）。
**源端真值是唯一安全的值；平台身份表达要不要改，是后端的决策不是客户端的。**

A、B 组**都失败且换遍等价类仍恒同** → 走 §1 铁律 8 止损：这不是客户端问题。
⚠️止损前自检等价类是否穷尽：**设备身份字段（oaid/markId/iosId）逐个试过非空真实值了吗**——
实测教训：穷举了渠道/包名/baseType/operators/UA/顺序却一直发空 oaid，把「后端拿 oaid 反查媒体号、
空值即 NPE」误判成「后端未配置」。空串不是等价类的自然成员，它常常就是病因本身。

### 2.7 伪造与合法对齐的边界（改设备身份字段前先过这道定义）

**伪造** = 发明源端不发的字段、或填源端不会产生的值（编假 IMEI、凭空加 mediaNo 字段——后端根本不认，白费一轮 build-test）。
**合法对齐** = 源端确实在发的字段，补成同语义的真实值（oaid 补持久 UUID——iOS本来就发持久 UUID；markId 同理）。
合法对齐**不属**「不伪造标识」类项目决策（D-013 等）的禁令范围——这类决策禁的是伪造，不是对齐；
按此定义可消解的"冲突"直接按对齐执行并留痕。定义消解不了的真冲突：不自行择一，探针取证→结构化登记→等裁决。

### 2.8 两件探针，主动被动配合用（修复循环的标准工具）

- **被动探针**（零成本，先看它）：事务失败单的 §3 已带 `failure_trace.signatures`
  （verify_outcome.py 自动从设备日志抓的逐请求 path→status/toast），**首个失败步直接可读**——
  先读它再定假设，别从终端症状开始剥洋葱。
- **主动探针**（秒级迭代）：按 §2.5 骨架在宿主机现场构造，一次往返 <1 秒。修复循环铁律：
  **每个假设先探针验证再改代码**——探针只发请求不改产物，不受产物侧决策禁令约束，
  单变量试完证实的修法再落码；装机分钟级回路只做最终验收（0815 实测：探针把回路从分钟级压到秒级）。

## 3. 环境闸：设备时钟（代价最高的一课）

### 3.1 判据

代码没动、昨天还通的登录，今天全链签名类拒绝。**先量时钟，别读代码**：

```text
python3 -c "import subprocess,time;d=subprocess.run('hdc shell date +%s',shell=True,capture_output=True,text=True).stdout.strip();print('skew(device-host)=',int(d)-int(time.time()),'s')"
```

> 示例：实测 -1126 秒（设备慢 18.8 分钟）。宿主机休眠后模拟器时钟必漂，且**漂了不会自己回来**。

### 3.2 机制

签名里的时间桶由后端拿**自己的**时钟重算，只接受当前桶 ±1。客户端签名再自洽也没用。
容忍窗用 §2.5 探针只挪 `ts` 就能扫出来。

### 3.3 校时

- `hdc shell date <MMDDhhmmYYYY.ss>` → `Operation not permitted`（hdc shell 是 uid 2000）；toybox 也没有 `hwclock`。
  **从 shell 校不了时。**
- 可行的只有**重启设备**，启动时从宿主 RTC 重新取时。
  ⚠️ 鸿蒙模拟器 reboot 后回来很慢（实测 >25 分钟仍未回、Emulator 进程 300%+ CPU），
  **模拟器是共享资源，重启前先问用户。**
- 长跑前顺手量一次 skew，比事后回溯便宜一个数量级。

## 4. A2H 认证链缺陷分类（按根因归类，修一类只需一处）

| 类 | 形态 | 判据 | 修法要点 |
|---|---|---|---|
| **名/值混淆** | header / 参数名写成iOS常量的**名** | grep 字面量对照iOS常量**值** | 引用同名常量，不写字面量 |
| **wire 形态不对齐** | UA / Content-Type charset / 平台字段形态 / 键序 | 两端原文 diff | 逐项对齐；对齐后保留，别反复拆装 |
| **死诊断** | 用自己假设验自己假设的自检矩阵 | 矩阵永远全绿 | 删掉，换成另一端基准 |
| **刷新钩子缺失** | iOS `onResume` 刷新，鸿蒙 Navigation 根内容无对位 | 登录后不切 tab 界面不变 | 数据侧推 AppStorage + `@StorageProp`（§6） |
| **登录态专属资源漏迁** | 登录/未登录两张默认头像共用一张 | 登录后头像仍是未登录占位 | 按登录态分流资源 |
| **登出不对称** | `clear()` 只清内存不清持久化 | 登出后冷启复登 | 一个 `clearSession()` 同时清运行时/AppStorage/持久化 |
| **冷启不种回** | 只抄 token/userId，丢 userState/nickName | 冷启昵称空白 | 从持久化整体 hydrate 再发请求 |
| **迟到应答冲状态** | 失败应答无条件重建会话 | 冷启变游客，日志里恢复与清除差几十 ms | "请求发出时的 token ≠ 当前 token 就丢弃"（§7.3） |
| **协议身份常量自造** | 渠道/包名/baseType/operators 被发明成平台化新值 | 对照组二分（§2.6）：换回源端真值即通 | 身份常量一律用源端真值；平台化表达是后端决策 |
| **注入槽空值** | 注入机械完整但值为空串（BuildProfile 空字段/空资源/未 configure 的钩子） | grep 注入槽实值；两轮 attempt 零提及密钥即此形态（外围全修、核心没查） | 值取 raw_apis.json 机械真值；表现为形态族，静态闸杀一个载体就换一个——终审靠业务态冒烟 |
| **后端身份供给缺失** | 服务器没为该包身份配映射行（媒体号/渠道表/设备注册） | 客户端可控字段等价类内结果恒同 | **客户端无修法**。探针证据 + external-deferred 登记，找后端配置（§1 铁律 8） |
| **引导链静默吞错** | 启动期游客/会话引导 `catch` 吞掉失败继续跑 | 首发症状漂移到下游（按钮上"用户未登录"/笼统文案），启动日志无痕 | 引导失败必须留痕（日志/状态标记），业务可以继续、痕迹不能没有；排查时**主动找启动期被吞掉的第一个失败** |

## 5. 动 UI 之前：先建"应答字段真值表"

**别猜某个接口回不回某字段。** 用 §2.5 探针把登录链每个接口各打一次，把关键字段列成表：

| 接口 | 回 token | 回 userState | 回 nickName | 回 avatar | 回 vip 信息 |
|---|---|---|---|---|---|
| initUser | | | | | |
| sendSmsCode | | | | | |
| bindMobile… | | | | | |
| getInfo | | | | | |

表填完，UI 侧的三个关键判断就有据可依，**不再需要猜**：

1. **登录成功那一刻本地是否已有足够数据切换界面**（若绑定接口已回 userState + nickName + userId → 是。
   那么界面没变就一定是刷新机制问题，不是"数据还没到"）。
2. **哪个接口的应答能当会话来源**（不回 token 的接口只能当档案补全）。
3. **哪些字段任何接口都不回**（如 avatar）→ 必须走本地默认资源；**哪些字段只有绑定接口回、初始化接口不回**
   （如 nickName）→ 冷启只能从本地持久化种回。

> 示例：真实项目里 `getInfo` 不回 token、两个接口都不回 avatar、`initUser` 不回 nickName——
> 这三条直接决定了 §6/§7 的修法。

## 6. "登录成功但界面不变"——一整类结构性缺陷

### 6.1 病根：iOS `onResume` 在鸿蒙侧没有对位钩子

iOS `Fragment.onResume() → setUserInfo()`：从登录 Activity 回来时宿主重新 resume，界面重读用户态自然刷新。
**iOS大量"回来就刷新"的逻辑都白嫖了这个钩子。**

鸿蒙侧若对位页面是某个 tab 的 `Navigation` **根内容**（不是 NavDestination），登录页以 NavDestination
压上去再 pop 回来时：组件实例**没被销毁重建** → `aboutToAppear()` 不重跑；根内容也**没有** `onShown` /
`onPageShow` 可用。于是"进页时拍一次快照"读到的永远是登录前的状态。

**实证方法**：登录页在栈顶时 `uitest dumpLayout` 一次——目标页的节点若仍与登录页节点在**同一棵树**里，
就是组件活着没重建，问题坐实。

> **推广**：凡是iOS靠 `onResume()` 刷新、鸿蒙对位页面落在 Navigation 根内容上的，都有这个洞。
> 迁移时看到 `onResume()` 里有 `setXxx()` / `refresh()`，就要专门想一次"鸿蒙这边谁来触发"。

### 6.2 修法：登录态走 AppStorage 响应式投影，不要快照

数据模型里加一个 `publishIdentity()`，把身份投影推进 `AppStorage`；页面用 `@StorageProp` 绑定：

```ts
// 数据模型 —— 单一 ingress/egress：saveUserInfo() 与 clear() 各调一次即可覆盖
//   登录 / 换绑 / 拉档案刷新 / 登出 / 注销 / token 过期回收 全部场景
publishIdentity(): void {
  AppStorage.setOrCreate<boolean>('user_is_binding', isBinding());
  AppStorage.setOrCreate<string>('user_nick_name', this.nickName);
  /* … token / user_id / user_state / head_url / vip … */
}
// 页面 —— @StorageProp 只读，写它编译报错，正好堵死"又去手抄字段"这条路
@StorageProp('user_is_binding') isBinding: boolean = false
```

**为什么不用项目里现成的 EventBus**：
1. `@StorageProp` 写入即重渲染，**不依赖任何生命周期钩子**——而病根恰恰是没有钩子；
2. 自研 EventBus 常见 `off(eventName)` 按名整批删：A 页退订会把 B 页同名订阅一起删掉，静默失效极难查；
3. 新增消费方零成本，不用回来改发布方。

⚠️ **代价**：AppStorage 从此是模型的投影。**任何绕过 `saveUserInfo()`/`clear()` 直接写字段的地方，
必须自己补一次 `publishIdentity()`**（示例项目里支付成功直写 `vipLevel` 就漏了一处）。

### 6.3 登录态专属资源

iOS侧登录/未登录的默认头像通常是**两张不同的图**。迁移时若两态共用一张，叠加"后端从不返回 avatar"（§5），
登录成功后头像仍是未登录占位。**判"是否显示成已登录"要逐个元素比，别只看用户名那一行。**

## 7. 登录 / 登出必须对称

### 7.1 登出要清持久化，不只是清内存

`clear()` 只清运行时单例 → Preferences 里 token/userId 原封不动 → 冷启初始化拿旧 token 又登回去，
"退出登录"形同虚设。正确的是一个 `clearSession()` = 清运行时（含 `publishIdentity()` 推登出态）
+ 清 AppStorage + 清持久化。**服务端 logout 失败也要就地清干净**，否则后续请求一路"未登录"。

### 7.2 冷启要从持久化整体种回

初始化接口的应答**可能不带 nickName**（§5）。iOS侧直接读 MMKV 所以重启后昵称照常；鸿蒙侧若只把
token/userId 抄进运行时模型，昵称/绑定态全丢。修法：初始化时先从持久化 `hydrateFrom(persisted)`
（连 userState / nickName / vipLevel 一起种上并推投影），再发网络请求。顺带修好弱网/离线冷启：
界面先按上次已知身份渲染，而不是先闪一下登出态。

### 7.3 ★迟到的失败应答会把刚恢复的登录态冲掉

**症状**：登录成功、登出对称也修好了，**杀进程冷启后仍变回未登录/游客**。

**排查法**：把启动期的请求发出、持久化恢复、应答返回、模型清除按时间戳排一列。典型形态：

```
T+0    某个启动期请求发出（此时会话还没恢复，token 为空）
T+127  持久化恢复完成，登录态就位 ✅
T+167  上面那个请求的应答回来 → 业务码"未登录"
T+167  拦截器见"未登录"就 clearSession() + 用空 token 重建游客会话   ← ★
T+627  真实登录态被游客态覆盖
```

**根因**：拦截器见"未登录"就无条件重建会话。iOS侧同位置通常**只发一个 UserLoggedOut 事件、不重建任何东西**，
这是迁移时"好心加的兜底"——看起来更健壮，实测有害。

**修法（判据要选对）**：

```ts
// ✅ 对：比"这条请求发出时用的 token"和"现在的 token"——不等就是迟到应答，丢弃
if (this.tokenAtRequest !== currentToken) return { handled: false };
// ❌ 错：if (isLogin()) return;   ← token 真过期时 isLogin() 也为真，会把恢复能力一起阉掉
```

`tokenAtRequest` 在请求 `await` 返回后、跑拦截器前**同步交棒**（中间不能有 `await`，否则被并发请求覆盖）。

> **可推广的教训**：异步栈里，**一条失败应答不该无条件改全局身份**。先问"这条应答还属于当前身份吗"。

## 8. 一次真实排障的时间线（说明"为什么方法比结论重要"）

- 8 轮盲猜（脱敏了 toastMsg、围绕 status 数字猜、自检矩阵同义反复）→ 0 进展
- 抓两端原文 10 分钟 → 定位头名混淆 → 协议通
- 次日同代码全链拒绝 → 量时钟 18.8 分钟 → 重启设备解决，代码零改动
- 主机侧直连探针 → 扫出时钟容忍窗、应答字段真值表 → UI 侧三处修法有据
- 界面不变 → dump 实证组件未重建 → AppStorage 投影
- 冷启掉登录 → 时间戳排序 → 迟到应答闸

每一步都是"先取证再动手"。反例是前 8 轮。

**第二例（同族问题、不同结局——说明止损也是产出）**：症状是发验证码弹"网络问题"。

- 网络栈日志第一刀（30 秒）→ `RespCode:200, errCode:0` → 出网了、服务器答了，排除明文/DNS/签名三类
- 主机探针复刻产物请求 → `/app/config` 业务 -500 `Missing request attribute 'platformInfo'`——文案骂字段缺失，字段明明发了
- 对照组二分 → 决定性字段=渠道号：产物自造 `channel='harmonyos'`，换回源端真值渠道号即通（客户端半个，可修）
- 继续走链 → `initUser` 卡 `mediaNo is null`；渠道×3、baseType×3、operators×3、包名、UA、请求顺序全排列**恒同** → 判定后端身份供给缺失，止损（后端半个，客户端无解，登记 external-deferred）
- 顺带定位症状漂移源：启动期游客引导 `catch` 静默吞错 → 用户看到的是下游按钮的笼统文案

从"网络问题"四个字到"半个客户端 bug + 半个后端配置缺口、各有归属"，全程零盲改。
**没修好后端不算失败——归因清、证据全、止损准，就是这次排障的完整产出。**

## 9. 验收清单（登录不是 `status=0` 就算过）

逐条看界面：

1. 未登录态：目标页显示未登录文案 + 未登录默认头像。
2. 登录成功后**不切 tab、不返回**，目标页当场变成：昵称 / ID / 已登录头像。
3. 切到别的 tab 再切回来——不应有任何跳变（两条路径读的是同一个源）。
4. 进账号页改完返回、买完会员返回——对应字段当场更新。
5. 「退出登录」→ 立刻变回未登录态 → **杀进程冷启**仍是未登录态（专抓 §7.1）。
6. 已登录状态下**杀进程冷启**：昵称/ID 立刻在，不是空白等网络（专抓 §7.2 / §7.3）。

任一条不过 = 登录未修完，按 §0 分诊表定位缺陷类。

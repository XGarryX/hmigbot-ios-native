# OAuth 2.0 通用流程与客户端职责边界

理解 OAuth 2.0 `authorization_code` 模式的职责分离是所有三方登录的基石。**客户端做错一步就是安全事故**。

## 1. OAuth 2.0 authorization_code 完整时序

```
                                                                          
   客户端         三方 SDK (微信/支付宝)     业务后端         三方开放平台服务器
     │                  │                     │                   │
     │ 1. 点击登录       │                     │                   │
     │─────────────────>│                     │                   │
     │                  │ 2. 拉起授权页        │                   │
     │                  │────────────────────────────────────────>│
     │                  │                     │                   │
     │ 3. 用户授权       │                     │                   │
     │<─────────────────│                     │                   │
     │                  │ 4. 返回 code         │                   │
     │<─────────────────│                     │                   │
     │                                        │                   │
     │ 5. 把 code 送到后端                     │                   │
     │────────────────────────────────────────>│                  │
     │                                        │ 6. 用 code+Secret │
     │                                        │   换 access_token │
     │                                        │──────────────────>│
     │                                        │                   │
     │                                        │ 7. 返回 token     │
     │                                        │<──────────────────│
     │                                        │                   │
     │                                        │ 8. 用 token 查    │
     │                                        │    用户信息        │
     │                                        │──────────────────>│
     │                                        │                   │
     │                                        │ 9. 返回 userInfo  │
     │                                        │<──────────────────│
     │                                        │                   │
     │                                        │ 10. 签发业务 token│
     │ 11. 业务 token + 用户信息               │                   │
     │<────────────────────────────────────────│                   │
     │                                                            │
     │ 12. 本地持久化                                             │
```

**要牢记的数字**：步骤 3-4 拿 code 是客户端职责；步骤 5-10 换 token + 查用户信息是**后端职责**；步骤 11 及以后是客户端职责。

## 2. 客户端职责边界（硬边界）

| 步骤 | 允许在客户端 | 原因 |
|---|---|---|
| 构造授权请求（scope/state）| ✅ | 纯参数构造，无敏感信息 |
| 拉起 SDK 调起授权 | ✅ | 必须 Page 层（需 UIAbilityContext）|
| 接收回调拿 code | ✅ | code 有时效（10 分钟）且一次性 |
| 把 code 发到自家后端 | ✅ | 正确做法 |
| 用 code 换 access_token | ❌ **绝不允许** | 需要 AppSecret，泄漏 = 黑产 |
| 用 access_token 查用户信息 | ❌ | 绕过后端审计，无法做业务风控 |
| 签发业务 token | ❌ | 业务 token 是后端的主权 |

## 3. 为什么 AppSecret 不能在客户端

三方平台颁发的 AppSecret / app_private_key 是商户身份凭证。泄漏后攻击者可：

- 用任意 code 换真实用户的 access_token
- 伪造登录请求冒充任意用户
- 调用三方平台的所有商户接口（消息推送、退款等）

客户端 APK / HAP 包可被反编译，字符串常量直接可见。**无论如何加密/混淆，打到客户端的密钥都是"公开的"**。

正确做法：
- AppID 可以放客户端（公开的身份标识）
- AppSecret / app_private_key **只放后端环境变量**（或 KMS）
- 后端启动时读密钥，运行时不落盘

## 4. state 防 CSRF 的原理

OAuth 2.0 规范强制要求 `state` 参数。原理：

```
正常流程：
  客户端生成随机 state → 带给三方平台 → 三方原样回传 → 客户端校验 state

CSRF 攻击：
  攻击者把自己的授权链接分享给受害者 → 受害者点击授权 →
  code 回到受害者 App → 受害者 App 把 code 送后端 →
  后端用 code 换到的是攻击者的 access_token →
  **后端把攻击者的账号信息绑到受害者账号上**
```

有了 state 校验：
- 客户端记下发出去的 state（内存或 sessionStorage）
- 回调里收到 state，对不上就拒绝

### 实现

```typescript
// 发起时
const state = 'login_' + Date.now() + '_' + Math.random().toString(36).substring(2, 10)
this.pendingState = state  // 存本地
authReq.state = state
WXApi.sendReq(context, authReq)

// 回调里
if (resp.state !== this.pendingState) {
  Logger.error(TAG, 'state mismatch, possible CSRF')
  return
}
this.pendingState = ''
```

`state` 只需在客户端内存保存即可（同一次授权生命周期内有效）。

## 5. 登录 vs 支付流程对比

两者都用同一套 SDK（微信 wxopensdk、支付宝 cashiersdk），但流程模型本质不同：

| 维度 | 登录（code 模式）| 支付（prepayId 模式）|
|---|---|---|
| 客户端拿的东西 | 一次性 code（10 分钟有效）| prepayId（2 小时有效）|
| 后端是否提前签 | ❌ code 来自三方，后端被动接收 | ✅ 后端先调三方生成 prepayId |
| 客户端是否持久化拿到的凭证 | ❌ code 拿到即转发后端 | ❌ prepayId 用完即弃 |
| 成功条件 | 后端换到用户信息 + 签发业务 token | 后端轮询订单状态为"已支付" |
| 签名由谁做 | 不需要客户端签名 | 后端按 WeChat/Alipay 规范签后送客户端 |

**共同点**：客户端都只是"中转 SDK 的返回值给后端"，**不参与核心决策**。

## 6. code 的一次性与时效

微信 code 规范：
- 有效时长 10 分钟
- 只能使用一次
- 过期或二次使用都会返回 `invalid code`

**实现含义**：
- 客户端拿到 code 后要**立即**发给后端，不能缓存
- 后端换 token 失败（如网络超时），客户端不能重试——必须重新走一遍授权流程
- 用户"停留在登录页 > 10 分钟"再点"登录"要注意，此时如果服务端把旧 code 存了，换 token 会失败

支付宝 authCode 规范类似：有效时长短、一次性。

## 7. 业务 token 的客户端持久化

后端签发的业务 token（非第三方 access_token）需要持久化：

- **存储**：Preferences（持久化）+ AppStorage（内存共享）
- **有效期**：由后端控制，客户端不关心
- **刷新**：过期后用 refresh_token 换（如后端支持），或者跳回登录页

**不存**：第三方 access_token。客户端不应接触这个值。

## 8. 静默登录 / 自动登录

后端签发的业务 token 有效期内，App 启动只需：
```
读取本地 token → 调 /user/getInfo 或类似接口 → 成功 = 已登录
                                             → 失败 401 = token 过期，清理本地，跳登录页
```

**不要**在 App 启动时自动调微信/支付宝 SDK 重新走 OAuth——那是"三方登录"，不是"自动登录"。自动登录只涉及本地 token + 后端 token 校验。

## 9. 常见误区

| 误区 | 正确做法 |
|---|---|
| "App 启动就调 SDK 静默登录" | 用本地业务 token 自动登录；没 token 才跳登录页 |
| "客户端缓存第三方 access_token 自己查用户" | 绝不允许；客户端只持业务 token |
| "code 换 token 失败重试 3 次" | code 一次性，失败只能重新走授权 |
| "state 固定写一个字符串" | 必须随机且每次不同 |
| "登录流程里把 AppSecret 写死" | 客户端绝不能有 AppSecret |
| "OAuth 登录成功立即在客户端 decode JWT 拿用户信息" | 用户信息来自后端返回，不要自己 decode |

## 10. 小结：一句话原则

> 客户端在 OAuth 里只干三件事：**构造授权请求** / **拿 code** / **发给后端**。其他都是后端的事。

把这条原则刻在脑子里，90% 的安全问题不会出现。

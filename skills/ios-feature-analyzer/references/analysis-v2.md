# 功能事实：沿完整行为提取

facts-view --scope feature 给出状态、写操作、分支、任务、持久化和系统调用线索。以用户入口/生命周期/后台入口为起点继续读完整调用链，函数与文件不直接等于 feature。

每个行为记录 input、precondition、processing、state transition、side effects、observable。保留边界数值、guard 的拒绝分支、Optional/nil/default、错误/重试、取消/重入、主线程/actor、弱引用和释放。图中的 token 片段不是已绑定的跨函数调用，接收者与泛型/宏/动态派发需要额外证据。

持久化必须记录 key/schema/序列化/写入/重读/业务读取/恢复失败。网络必须记录服务参数、鉴权、编码、响应和错误到用户反馈。状态要区分值复制与对象共享；不能把普通 var 直接翻译成全局 store。

AC 按行为与源中实际分支制定，无数量上限。每项给独立真值，unit 用源规则与边界样本，contract 用真实协议样本，ui/device 用真实动作与观察。任何只能由静态扫描看到的调用不能宣告运行通过。

输出模板：稳定 F ID/source anchors、行为链、状态转移表、边界与错误、并发/取消/lifetime、存储/服务契约、独立 AC、unknown 和平台决策。把每条机器 obligation 绑定真实 AC 与 source_review；一个 AC 可以覆盖多个事实，但场景必须具体。

失败恢复：有信号无义务属规则 bug；有义务无 AC 回 spec；无独立 oracle 保持 unknown；目标缺实现交 execute。复核人与代码作者分开记录，不能从生成的目标结果反推 expected。

## 逐动作执行步骤

1. 从可达入口列动作和实际调用接收者；同名方法、protocol 要继续追实现与注入点。
2. 打开 handler、状态写入、服务实现和回调的完整片段。记录每次写入发生的时点，不能只摘最终赋值。
3. 对同步返回、异步完成、错误/取消、再次触发分别填写下表；只展开源码存在的分支。源中无法确定的顺序写 unknown、原因和补证位置。
4. 对共享状态/副作用选一个合同作者。进入 Spec 后按 [动作合同](../../a2h-spec/references/action-contracts.md) 定义一次，UI、功能和 AC 引用同一动作 ID。
5. 用至少一个正常场景和一个源码存在的失败/取消场景回走完整链路；复核者独立检查源片段和跨文档投影，不能依据生成结果反推期望。

## 通用正反例：异步取消

假设源 handler 先写 `cancelRequested=true`，调用任务 `cancel()`；完成回调再从队列移除。应记录三个时点：点击后标记取消、请求停止、完成回调移除；还要读出回调是否可能成功、旧回调是否仍能写状态、重复取消如何处理。目标接口必须保留这个合同，或引用已批准差异。

合格描述：“点击后本项显示正在取消；调用取消请求；队列成员在完成回调分支移除，失败反馈按该分支处理。”每句分别附真实源锚点。若源实际立即移除，应忠于源写立即移除，示例不能覆盖应用事实。

不合格描述：“取消即清空队列”“cancel()返回即操作完成”“所有异步任务取消后都不会回调”。它们把请求和完成合并，可能导致丢进度、错误重试或回调写入已释放对象。脚本只能核对动作引用和字段，取消语义须由源码复核裁定。

## 通用正反例：清理的完成边界

假设点击清理先清空内存列表，再在后台删除文件。分开记录 UI 列表清空、内存对象释放、磁盘删除结束/失败及重启后重载结果；公开 `clear()` 的返回是“已提交”还是“已完成”要从实现确认。

合格描述把即时效果与完成事件分开，并给删除失败、离开页面和重开时的源行为。没有重试或错误提示就如实注明，不为完善模板增加功能。

不合格描述：“页面清空证明文件删除成功”“服务是异步所以UI也等待删除”。UI和服务文档应引用同一合同，不能各自推导另一层完成时点。

# 验证执行与证据复用

本规范使用 [稳定编号与范围](check-keys-and-scope.md) 的 CHECK-1 至 CHECK-7；没有实际适用输入或未选择高级观察时，不机械要求全部调用。每项按实际产品、授权范围和可用能力执行；文件报告始终可以输出，完整验收状态由各轴的真实证据决定。

## 状态与适用范围

- PASS：本项实际执行且证据与当前输入、配置和产物绑定有效。
- FAIL：已定位具体产品、构建、资源或行为缺陷，给出对象、后果和恢复条件。
- DEFERRED / not_run：前置能力、授权或所需观察不存在。记录恢复条件，不冒充 PASS，也不自动扩大为无关检查失败。
- 纯文字命中、名称可疑、机械比例与记录元数据属于提示，不能直接变成产品错误。

CHECK-6 路由静态分析可在设备不可用时独立进行；CHECK-7 依赖的运行或视觉观察仅在实际授权和能力存在时执行。当前禁止界面读取、截图和设备远控时，使用已有 CLI/文件证据，否则如实记 not_run。委托后的 PASS/FAIL 必须读取实际产物并核对输入身份。

## 构建和复检

真实 SDK 构建命令成功且配置、当前输入和产物绑定一致时，合法缓存命中有效；不通过 touch 或 clean 人为制造重新编译。产品输入或 SDK/配置变化使旧构建证据失效，须重跑对应构建。

每个 detector 按规则版本、所选产品、配置及实际输入签名运行。同签名的完整原始结果可被多个阶段引用，记录原调用和本次复用；不得复用缺失、篡改、失败不完整或输入过期的结果。修复只使真正依赖其变化的检查失效，不机械重跑全部项目。

## 失败与恢复

自动修复的轮数是同一路径的上限。无进展时停止该路径，保留真实缺陷及受影响消费者，评估可用替代技术路径；不因次数要求新的产品审批，也不无限重试。用户预算、授权边界和实际产品取舍仍需遵守。

不修改 verifier 的原始结果来宣称通过；状态应由原检查生产者或其可回放适配器生成。独立的构建、静态诊断和进度报告可以继续。

## 报告

始终允许生成 `spec/verify-report.md`：包括 partial、failed、DEFERRED 和 not_run 状态、已完成轴、原错误、可执行备选路径及各路径的证据边界。输入缺失或尚未实测不能成为“禁止写报告”的理由。

完成态只使用当前有效证据；未执行不得写 PASS，未观察冷启不等于已发现崩溃，纯静态通过不等于完整运行等价。业务字段、所有权或源/目标绑定变更仍须被对应合同识别。

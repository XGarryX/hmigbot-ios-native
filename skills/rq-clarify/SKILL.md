# rq-clarify — 需求澄清

> 通过交互式问答，将模糊需求转化为清晰、完整、可执行的需求描述，并完善特性清单和需求规格的细节。

## 定位

好的软件需求应该是"无歧义的"。但现实中，用户很少一开始就能把需求说清楚。rq-clarify 的职责就是通过恰当的提问，把这些"默认值"显性化，并配合完善 proposal.md 中的特性清单和需求规格。

核心原则：**问得少，问得准**。不是把所有可能的问题都抛出来，而是只问那些真正影响质量的关键问题。

注意：竞品调研已移至 rq-parse，rq-clarify 专注于需求细节的澄清和确认。

## 输入

- 用户提供的需求描述（可以是模糊的）
- 或 `rq-parse` 的结构化分析结果（包含模糊点列表）
- proposal.md 草稿（包含待完善的特性清单和需求规格）

## 澄清策略

### 提问优先级

```
blocker 模糊点（必须澄清）
  ↓ 优先处理
important 模糊点（影响质量，尽量澄清）
  ↓ 次优先
nice-to-have 模糊点（告知用户，不强制追问）
```

### 提问批次控制

- **每轮最多 3-5 个问题**
- **相关问题合并**：多个模糊点指向同一个功能区域时，合并为一个综合问题
- **依赖问题串联**：问题 B 的答案取决于问题 A 时，先问 A
- **提供选项而非开放题**：尽量给出可选方案让用户选择

### 提问模板

#### 范围模糊 → 边界界定法

```
你提到"XX功能"，我理解可能包括以下几个方面：
1. [方面A] — 例如...
2. [方面B] — 例如...
3. [方面C] — 例如...

本次需求是要覆盖哪些？有没有明确不做的？
```

#### 行为模糊 → 场景还原法

```
关于[某个行为]，我想确认几个场景下的预期表现：
- 场景1：当用户[做某事]时，应该发生什么？
- 场景2：如果[某个条件]不满足，该怎么处理？
- 场景3：[边界情况]下的预期行为是？
```

#### 交互模糊 → 原型描述法

```
关于[某个交互]，目前有两种常见的实现方式：
- 方案A：[描述交互方式A]，适合[场景]
- 方案B：[描述交互方式B]，适合[场景]

你倾向哪种？或者有其他想法？
```

#### 数据模糊 → 字段枚举法

```
关于[数据实体]需要保存哪些信息，我列了一个初步清单：
- [字段1]：[说明]（必须/可选）
- [字段2]：[说明]（必须/可选）
- ...

有需要增减的吗？
```

#### 约束模糊 → 量化锚定法

```
你提到[某个非功能要求]，我需要一个可衡量的标准：
- 目前的表现大约是[基线]（如果已知）
- 你期望达到的目标是？（例如：响应时间<Xms，文件大小<YMB）
- 有没有硬性的底线要求？
```

#### 兼容模糊 → 影响枚举法

```
这个变更可能影响以下现有功能：
- [功能A]：[可能的影响]
- [功能B]：[可能的影响]

需要确保这些功能的行为不变吗？还是允许部分调整？
```

## 通用技术选型澄清

### 数据存储方案选择
```
关于数据存储，这个功能适合用：
- 键值存储（Preferences/KV）：适合简单配置项、开关、少量数据
- 关系型数据库：适合结构化数据、需要复杂查询
- 文件存储：适合大文件、二进制数据、缓存

你的数据特征更接近哪种？大约有多少条数据？
```

### 离线/在线策略
```
这个功能在没有网络时：
- 完全不可用？（纯在线功能）
- 使用缓存数据，但不能更新？
- 需要支持离线操作，联网后同步？
```

### 后台行为
```
这个功能是否需要在后台继续运行？
- 如果需要：短时任务（秒级）还是长时任务？
- 后台任务的实现方式会影响架构设计。
```

### 权限/安全需求
```
这个功能可能涉及以下权限或安全控制：
- [权限1]：用于[目的]
- [权限2]：用于[目的]

需要确认：用户拒绝权限时的降级方案是什么？
```

## 特性清单与需求规格澄清

在处理完模糊点后，需要配合完善 proposal.md 中的特性清单（§5）和需求规格（§6）。

### 特性清单确认

对每个特性（F1、F2...），向用户确认：

```
关于 F1 {特性名称}：
- 功能描述是否准确？
- 用户价值是否完整？
- 有没有遗漏的技术要点？
- 有没有性能、安全或其他非功能要求？
- 是否需要拆分为子特性（F1.1、F1.2）？
```

对于子特性，确认粒度是否合适：

```
F1 是否需要拆分为多个子特性？
- 如果需要，子特性有哪些？
- 每个子特性的职责边界是什么？
```

### 需求规格确认

对每个需求规格（R1、R2...），向用户确认：

```
关于 R1 {需求名称}：
- 描述是否清晰？
- 需求价值：这条需求解决什么问题？为什么对你/用户有价值？
- 使用场景：在什么场景下会触发这条需求？
- 验收标准 AC1/AC2 是否可验证？
- 有没有具体的量化指标（如响应时间<100ms、并发>1000）？
- 优先级 P0/P1/P2 是否合适？
- 与其他需求的依赖关系是否准确？
```

### 核心问题与边界确认

在需求澄清结束时，确认§1 的核心问题和边界：

```
关于需求边界，我确认一下：
1. 核心问题：{AI 理解的要解决的核心问题}，这个理解是否准确？
2. 不做什么：{AI 理解的明确不做的功能}，有没有遗漏或错误？
3. 功能边界：还有没有应该包含但没列出的功能？有没有不应该包含但列出的功能？
```

### 验收标准细化

对于验收标准不明确的需求，使用量化锚定法：

```
对于 R1 的验收标准，你提到需要"快"，我需要可衡量的指标：
- 目前的表现大约是[基线]（如果已知）
- 你期望的目标是？（例如：响应时间<Xms、文件大小<YMB）
- 有没有硬性的底线要求？
```

## 系统架构澄清（新增）

在特性清单与需求规格确认完成后，进入 delta-spec.md 阶段前，需要配合完善 proposal.md 中的系统架构概述（§6）。

### 架构图来源确认

询问用户架构图的来源方式：

```
关于 §6 系统架构概述：
你有现成的架构文档吗？
- 有：提供文件路径，我将从 {文件路径} 扫描 arch.md 或相关架构文件，提取架构图和模块职责
- 没有：基于已确认的特性清单和模块依赖关系，我将生成一个概念架构图供你确认
- 不需要：本需求简单或无需架构图，可标注"不适用"后跳过
```

### 有现成架构文档时

1. 扫描用户提供的文件路径，查找 `arch.md`、`architecture.md`、`design.md` 等架构文件
2. 提取架构图（如有）和模块职责描述
3. 询问用户：
   ```
   我从 {文件路径} 找到了以下架构内容：
   - 架构图：{描述}
   - 核心模块：{列表}
   
   这些内容是否适用于本需求？是否有需要调整或补充的地方？
   ```

### 无现成架构文档时

基于已确认的特性清单（F1、F2...）和需求，生成概念架构图：

```
关于 §6 系统架构概述，基于已确认的特性清单，我生成了以下概念架构：

```
{ASCII 架构图示例：
       ┌─────────────────────────────────────┐
       │           用户态/应用层              │
       │    模块A      │      模块B           │
       └───────┬───────┴──────────┬──────────┘
               │                  │
       ┌───────▼──────────────────▼──────────┐
       │            核心服务层                │
       │  模块C  │  模块D  │  模块E           │
       └───────┬───────┬──────────┬──────────┘
               │       │          │
       ┌───────▼──┐   │    ┌─────▼──────┐
       │ 数据存储层│   │    │ 外部依赖层  │
       └──────────┘        └────────────┘
```

核心模块职责：
- 模块A：{描述}
- 模块B：{描述}
...

请确认：
1. 模块划分是否合理？
2. 模块职责描述是否准确？
3. 模块之间的交互关系是否正确？
4. 是否有遗漏的模块或需要合并的模块？
```

### 模块交互确认

对架构中的模块交互关系，向用户确认：

```
关于模块之间的交互：
1. 数据流：哪些模块之间有数据传递？方向是什么？
2. 调用关系：哪些模块调用哪些模块？
3. 依赖关系：哪些模块是底层模块，被其他模块依赖？
4. 不涉及的模块：本需求**不涉及**或**不改动**哪些现有模块？
```

### 架构澄清输出格式

```markdown
### 系统架构确认
| 项目 | 确认状态 | 内容 |
|------|---------|------|
| 架构图 | ✅ 确认 / 🟡 待调整 | {架构图或"不适用"} |
| 模块职责 | ✅ 确认 / 🟡 待调整 | {模块列表} |
| 模块交互 | ✅ 确认 / 🟡 待调整 | {交互关系描述} |
| 不涉及的模块 | ✅ 确认 | {列表} |
```

## 交互流程

```
接收需求或模糊点列表
    ↓
按优先级排序 → 分批提问
    ↓
第 1 轮提问（blocker 级别，3-5 个问题）
    ↓
← 用户回答
    ↓
分析回答 → 更新需求理解 → 检查是否引入新模糊点
    ↓
[如有未解决的 blocker/important] → 下一轮提问
    ↓
... 重复直到关键模糊点解决 ...
    ↓
生成澄清后需求摘要 → 用户确认
    ↓
[如有 proposal.md 草稿] → 进入特性清单与需求规格确认
    ↓
确认特性细节 → 确认需求规格细节
    ↓
[如有需要] → 确认系统架构概述（§6）
    ↓
输出完整澄清结果
```

### 用户回答处理

- **回答偏离问题**：温和地重新引导
- **回答"我不确定"**：提供合理的默认建议
- **回答引入新需求**：记录下来，但提醒聚焦原始需求
- **用户表示"别问了，你决定"**：基于行业最佳实践做出合理假设

### 提前终止

- 用户明确表示"够了"或"就这样"
- 所有 blocker 模糊点已解决
- 用户要求直接进入下一步

提前终止时，将未澄清的点标记为 `assumption`（假设）。

## 示例

### 示例 1：从模糊到清晰

**原始需求中的模糊点**：
1. [blocker] "离线下载"——下载整个播客系列还是单集？
2. [blocker] 下载的文件存在哪里？用户能管理已下载文件吗？
3. [important] 下载时的网络策略——仅 WiFi 还是允许移动数据？
4. [nice-to-have] 下载文件格式是否需要转换？

**第 1 轮提问**：

> 关于离线下载功能，我需要确认几个关键点：
>
> 1. **下载范围**：用户可以下载单集还是整个播客系列？
>    - A. 仅支持单集下载
>    - B. 支持单集和批量下载（整个系列或多选）
>
> 2. **文件管理**：用户是否需要一个"下载管理"页面来查看、删除已下载的文件？
>
> 3. **网络策略**：下载时的默认网络策略是？
>    - A. 仅 WiFi（推荐，播客文件通常较大）
>    - B. WiFi + 移动数据
>    - C. 让用户自己在设置里选

**用户回答**：
> "1选B，2要的，3选C但默认仅WiFi"

**澄清后摘要**：
> 离线下载功能支持单集下载和批量下载（按系列或多选）。提供下载管理页面用于查看进度、删除已下载文件。网络策略默认仅 WiFi，用户可在设置中切换为 WiFi+移动数据。

### 示例 2：特性清单与需求规格确认

**背景**：用户已完成竞品调研，proposal.md 草稿中已产出特性清单和初步需求规格

**proposal.md 草稿内容**：
```
## 1.5 背景与价值
#### 核心问题
{待确认}

#### 不做什么（边界）
{待确认}

## 5. 特性清单
- F1: 资源高负载检测 — 功能描述：检测CPU/内存高负载 — 用户价值：及时发现性能问题

## 6. 需求规格
- R1: CPU 高负载检测 — 描述：周期性检测 CPU 使用率 — AC1: (待细化)
```

**rq-clarify 继续提问**：

> 关于 F1 资源高负载检测，我需要确认几个细节：
>
> 1. **检测指标**：除了 CPU 和内存，是否还需要检测 IO、网络或存储空间？
>
> 2. **检测周期**：你希望多久检测一次？（例如：1s/5s/10s）
>
> 3. **是否需要拆分子特性**？例如 F1.1 CPU 检测、F1.2 内存检测？
>
> 关于 R1 CPU 高负载检测：
>
> 1. **需求价值**：CPU 高负载检测解决什么问题？为什么有价值？
> 2. **使用场景**：在什么场景下会触发？
> 3. **阈值**：CPU 使用率超过多少算"高负载"？
>    - A. 80%（宽松）
>    - B. 90%（标准）
>    - C. 95%（严格）
> 4. **持续时间**：CPU 超过阈值多久才触发告警？（例如：3s/5s/10s）

**用户回答**：
> "1只检测CPU和内存，2周期5s，3不需要子特性，4解决卡顿问题，5野线程死循环场景，6阈值90%，7持续5s"

**确认后输出**：
```
### 核心问题与边界确认
| 项目 | 确认状态 | 内容 |
|------|---------|------|
| 核心问题 | ✅ 确认 | 检测缺位：无统一组件持续判断系统是否高负载 |
| 不做什么 | ✅ 确认 | 不做处置动作，只做检测和取证 |

### 特性清单确认
| 特性 | 确认状态 | 补充/修改内容 |
|------|---------|--------------|
| F1 资源高负载检测 | ✅ 确认 | 明确只检测 CPU 和内存，周期 5s；不拆分子特性 |

### 需求规格确认
| 需求 | 确认状态 | 补充/修改内容 |
|------|---------|--------------|
| R1 CPU 高负载检测 | ✅ 确认 | 需求价值：解决卡顿问题；使用场景：野线程死循环；AC1: CPU≥90% 持续 5s 触发 |

### 示例 3：系统架构确认

**背景**：特性清单和需求规格已确认，需要完善系统架构概述

**rq-clarify 提问**：

> 关于 §6 系统架构概述：
>

# ArkTS 功能修改问答技能

## 概述

本技能专注于ArkTS语言的Harmony应用代码仓功能修改类问题回答。当开发者询问"给xx增加开关/参数/流程怎么做？"、"新增视频播放怎么实现？"等功能修改问题时，本技能基于arkts-locator提供的定位信息，分析代码仓实际情况，给出具体的功能修改建议和实现方案。本技能仅提供问答和建议，不直接修改代码。

## ArkTS V1 / V2 双版本兼容说明

本项目锁 V2（API 12+）。代码仓中可能既存在 V1 旧代码也存在 V2 新代码。本技能给出的功能修改建议遵循以下规则：

1. **新增代码一律使用 V2 装饰器**（项目目标风格）
2. **修改现有 V1 文件**：在保持现有装饰器一致的前提下扩展，**不要混合 V1 / V2**（同一个 struct 不能既有 `@State` 也有 `@Local`）；若需引入 V2 特性（如 `@Computed`、`@Trace` 属性级观察），先把整个文件迁移到 V2
3. **修改建议中需明确标注**：当前文件是 V1 还是 V2，以及推荐的修改方案版本

V1 → V2 装饰器映射（修改方案中常用）：

| V1 装饰器 | V2 装饰器 | 修改建议时的说明 |
|---|---|---|
| `@Component` | `@ComponentV2` | 新增 struct 用 V2 |
| `@State` | `@Local` | 组件内状态 |
| `@Prop` | `@Param`（只读加 `@Once`，可写省略 `@Once`） | 父→子单向 |
| `@Link` | `@Param + @Event` 回调 | V2 没有 `@Link`，必须用回调模式 |
| `@Provide` / `@Consume` | `@Provider()` / `@Consumer()` | 跨层级，V2 必须带括号 |
| `@Observed` + `@ObjectLink` | `@ObservedV2` + 类属性 `@Trace`（无 `@ObjectLink`） | 跨组件对象观察 |
| `@StorageLink` / `@StorageProp` | `AppStorageV2.connect(Cls, key, () => new Cls())` | 全局存储，需先抽出 `@ObservedV2` 类 |
| `@LocalStorageLink` / `@LocalStorageProp` | `@Provider()/@Consumer()` 或页面根 `@Local`+`@Param`（无 LocalStorageV2） | 同上 |
| `PersistentStorage.persistProp` | `PersistenceV2.globalConnect(...)` | 一站式持久化 + 响应式 |
| `@Watch` | `@Monitor` + `IMonitor` | 监听属性变化 |
| —（V1 无） | `@Computed` | V2 新增：派生状态缓存 |

**修改方案设计时常用的 V1+V2 兼容 grep**（用于在受影响的文件中快速定位修改点）：

- 组件：`@Component(V2)?\b`
- 状态：`@State|@Local`、`@Prop|@Param`、`@Link|@Event`
- 全局/持久化：`@StorageLink|@StorageProp|AppStorageV2|PersistentStorage|PersistenceV2`
- 监听：`@Watch|@Monitor|@Computed`

## 功能修改类问题类型

本技能支持以下9大类功能修改问题：

### 1. UI组件功能扩展
**问题特征**：询问UI组件的新功能、交互、样式修改
**典型问题**：
- "给列表项增加长按删除按钮"
- "给卡片组件增加展开/收起开关"
- "给按钮增加点击缩放动画"
- "给弹窗增加拖拽功能"
**修改建议位置（V1+V2 兼容）**：组件装饰器（V1 `@Component` / V2 `@ComponentV2`）、build方法、事件处理函数（V2 用 `@Event` 子→父回调，V1 用 `@Link` 双向绑定）、样式配置（`@Styles`/`@Extend` V1/V2 通用）

### 2. 状态与数据流增强
**问题特征**：询问状态变量、数据流、存储的扩展
**典型问题**：
- "给用户信息增加年龄字段"
- "给购物车增加多选状态"
- "给列表数据增加加载状态标识"
- "给缓存增加过期时间配置"
**修改建议位置（V1+V2 兼容）**：
- 组件内状态：V1 `@State` / V2 `@Local`
- 父→子：V1 `@Prop` / V2 `@Param`（+ `@Once` 只读）
- 父↔子：V1 `@Link` / V2 `@Param + @Event` 回调
- 跨层级：V1 `@Provide / @Consume` / V2 `@Provider() / @Consumer()`
- 可观察类：V1 `@Observed + @ObjectLink` / V2 `@ObservedV2 + @Trace` 属性
- 全局：V1 `@StorageLink / @StorageProp` / V2 `AppStorageV2.connect`
- 本地：V1 `@LocalStorageLink / @LocalStorageProp` / V2 `@Provider`/`@Consumer` 或页面根 `@Local`+`@Param`（无 LocalStorageV2）
- 持久化：V1 `PersistentStorage.persistProp` / V2 `PersistenceV2.globalConnect`
- 监听：V1 `@Watch` / V2 `@Monitor + IMonitor`
- 派生状态（V2 新增）：`@Computed`
- 数据模型、Preferences/RdbStore：V1/V2 通用

### 3. 网络请求与API扩展
**问题特征**：询问API调用、网络请求的扩展
**典型问题**：

## 工作流程

### 步骤1：功能修改问题类型识别

**目标**：识别用户问题的具体功能修改类型

**操作流程**：
1. **关键词分析**：
   - 提取问题中的动词（增加、新增、修改、优化、集成等）
   - 提取问题中的目标对象（组件、页面、接口、数据等）
   - 提取问题中的功能描述（开关、参数、流程、动画等）

2. **类型匹配**：
   - 根据关键词组合匹配到10大类问题类型
   - 确定问题的核心修改方向
   - 识别问题的复杂度（简单参数调整 vs 复杂功能集成）

3. **问题拆解**：
   - 对于复杂问题，拆解为多个子任务
   - 确定每个子任务的修改类型
   - 建立修改任务的优先级和依赖关系

**输出**：问题类型识别结果，修改任务清单，复杂度评估

### 步骤2：基于locator信息的代码定位

**目标**：利用arkts-locator传递的定位信息，了解修改涉及的代码范围

**操作流程**：
1. **加载locator信息**：
   - 获取arkts-locator提供的定位结果
   - 解析核心文件清单和关键入口点
   - 分析代码模块的依赖关系

2. **定位范围确认**：
   - 确认功能修改涉及的主要文件
   - 识别受影响的组件和模块
   - 分析修改的传播影响范围

3. **入口点识别**：
   - 确定功能的主要入口点
   - 识别关键的配置位置
   - 分析数据流转路径

**输出**：修改涉及的核心文件清单，关键入口点，影响范围分析

### 步骤3：基于DAG组合的代码读取

**目标**：根据问题类型和locator信息，选择对应的DAG组合读取代码

**操作流程**：

#### DAG选择策略
根据问题类型选择对应的DAG组合：

**UI组件功能扩展** → DAG_UICOMPONENT
```
locator[components] → component_definition → build_method → event_handlers → styles
```
1. 读取组件定义文件（V1+V2 兼容：`@Component(V2)?\b` 装饰器）
2. 分析build方法的UI结构
3. 查看事件处理函数（onClick、onAppear 等；V2 还含 `@Event` 子→父回调）
4. 检查样式配置（@Styles、@Extend 等，V1/V2 通用）

**状态与数据流增强** → DAG_STATE
```
locator[stores] → state_variables → data_models → storage_services → data_flow
```
1. 读取状态管理文件（V1+V2 兼容）：
   - 组件内：`@State|@Local`
   - 父→子：`@Prop|@Param`
   - 父↔子：`@Link|@Event`
   - 可观察类：`@Observed(V2)?\b`，V2 还需 `@Trace`
   - 全局/本地/持久化：`@StorageLink|@StorageProp|AppStorageV2|PersistentStorage|PersistenceV2`
   - 监听/派生：`@Watch|@Monitor|@Computed`
2. 分析数据模型定义
3. 查看存储服务实现
4. 追踪数据流转路径

**网络请求与API扩展** → DAG_NETWORK
```
locator[services] → api_definitions → http_client → interceptors → data_transformers
```
1. 读取API接口定义
2. 分析HTTP客户端配置
3. 查看拦截器实现
4. 检查数据转换逻辑

**页面功能新增与增强** → DAG_PAGE
```
locator[pages] → page_components → router_config → navigation → page_params
```
1. 读取页面组件定义
2. 分析路由配置文件
3. 查看Navigation组件使用
4. 检查页面参数传递机制

**多媒体功能集成** → DAG_MEDIA
```
locator[media] → media_components → player_services → media_utils → permissions
```
1. 读取媒体组件实现
2. 查看播放器服务
3. 检查媒体工具函数
4. 分析权限申请逻辑

**交互逻辑与流程调整** → DAG_INTERACTION
```
locator[business] → event_handlers → business_logic → flow_control → validation
```
1. 读取事件处理函数
2. 分析业务逻辑实现
3. 查看流程控制代码
4. 检查验证逻辑

**动画与特效增强** → DAG_ANIMATION
```
locator[components] → animation_configs → animate_methods → component_props → transitions
```
1. 读取动画配置
2. 查看animateTo方法调用
3. 检查组件动画属性
4. 分析transition定义

**设备能力与硬件交互** → DAG_HARDWARE
```
locator[services] → device_apis → permission_manager → data_processor → event_listeners
```
1. 读取设备API调用
2. 查看权限管理器
3. 检查数据处理模块
4. 分析事件监听器

**性能优化与体验改进** → DAG_PERFORMANCE
```
locator[components] → performance_configs → cache_strategies → lazy_loading → render_optimizations
```
1. 读取性能配置
2. 查看缓存策略
3. 检查懒加载实现
4. 分析渲染优化代码

**输出**：代码读取结果，关键代码片段，文件重要性评估

### 步骤4：功能修改方案设计

**目标**：基于代码分析，给出符合SOLID原则的修改方案

**操作流程**：
1. **SOLID原则应用**：
   - **单一职责**：确保修改点职责单一，不引入过多功能
   - **开闭原则**：优先通过扩展而非修改实现新功能
   - **里氏替换**：确保继承关系的一致性
   - **接口隔离**：避免不必要的依赖接口
   - **依赖倒置**：依赖抽象而非具体实现

2. **修改位置判断**：
   - **最佳修改位置**：根据代码结构和SOLID原则确定最合适的修改点
   - **扩展方式选择**：选择装饰器、组合、继承等合适的扩展方式
   - **配置化设计**：对于开关、参数等，考虑配置化管理

3. **实现方案设计**：
   - **代码结构设计**：设计新增代码的组织结构
   - **接口定义**：定义必要的接口和类型
   - **数据流设计**：设计数据流转和状态更新机制
   - **错误处理**：设计异常处理和边界情况处理

4. **影响范围评估**：
   - **前向影响**：评估修改对下游代码的影响
   - **后向影响**：评估修改对上游依赖的影响
   - **横向影响**：评估修改对同层模块的影响

**输出**：修改方案设计，最佳修改位置，实现建议，影响范围评估

### 步骤5：回退机制和重试策略

**目标**：在无法回答或出错时提供备选方案

**错误类型**：

#### 1. 定位信息不足
- **表现**：locator提供的信息不足以确定修改位置
- **处理**：
  1. 回退到步骤2，重新分析locator信息
  2. 尝试使用repomap自行定位相关模块
  3. 向用户请求更多上下文信息

#### 2. 代码理解偏差
- **表现**：代码结构理解不准确，导致修改方案不可行
- **处理**：
  1. 回退到步骤3，重新读取相关代码
  2. 选择不同的DAG组合探索代码
  3. 扩展代码读取范围

#### 3. 修改方案冲突
- **表现**：修改方案与现有代码结构冲突
- **处理**：
  1. 回退到步骤4，重新设计修改方案
  2. 考虑不同的扩展方式
  3. 评估是否需要重构现有代码

#### 4. 信息不完整
- **表现**：代码仓中缺少必要的实现或配置
- **处理**：
  1. 承认信息不足，不进行假设
  2. 向用户明确说明缺失的部分
  3. 请求用户提供更多信息或确认需求

**回退机制**：
1. **步骤级回退**：当前步骤失败时，返回上一步重新尝试
2. **DAG路径回退**：当前DAG探索失败时，尝试其他DAG路径
3. **降级策略**：当三次重试失败后，使用repomap重新定位

**重试策略**：
1. **三次重试机制**：每个步骤最多重试3次
2. **备选方案**：每次重试采用不同的策略
3. **人工干预**：重试失败后，向用户请求澄清

## 使用示例

**用户问题**："给列表项增加长按删除功能怎么做？"

**技能执行流程**：

**步骤1：问题类型识别**
- 识别为"UI组件功能扩展"类型
- 问题关键词：列表项、长按、删除功能
- 复杂度：中等（涉及事件处理、UI更新、数据修改）

**步骤2：基于locator信息定位**
- locator提供的核心文件：`entry/src/main/ets/pages/ItemList.ets`
- 关键入口点：`List`组件、`ListItem`组件、事件处理函数
- 影响范围：列表页面、数据管理模块

**步骤3：基于DAG_UICOMPONENT读取代码**
```
读取ItemList.ets → 识别 V1/V2 → 分析build方法 → 查看ListItem定义 → 检查事件处理
```
发现代码结构（示例文件为 V2）：
- 使用`List`和`ListItem`组件
- 当前只有`onClick`事件
- 数据通过 `@Local`（V2）管理；如为 V1 文件则通过 `@State` 管理

**步骤4：修改方案设计**
- **最佳修改位置**：`ItemList.ets:build方法中的ListItem组件`
- **SOLID原则**：开闭原则，通过扩展事件处理而非修改组件
- **实现方式（V2 示例）**：
  1. 在`ListItem`上添加`onLongPress`事件
  2. 新增删除函数`deleteItem(index: number)`
  3. 更新 `@Local` 状态中的数据（V1 文件则更新 `@State`）
  4. 添加删除确认对话框
- **版本一致性提示**：若现有文件是 V1，新增逻辑保持 V1 装饰器一致；若需引入 V2 特性（如 `@Computed`），先把整个文件迁移到 V2，避免混用

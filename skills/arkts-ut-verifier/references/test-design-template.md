# 测试用例方案模版（UT Design）

第一步「测试用例设计」的产物格式。**每个功能点（一个 Feature）输出一份**，写到
`spec/test/ut-design/F{编号}_{英文名}.md`。

设计的输入有两个：

1. **Spec**：`spec/baseline/features/F*.md` 的 `## 验收标准`（每条 `- [ ]` 是一个验收点）
2. **代码**：`entry/src/main/ets/` 下与该 Feature 相关的 model / service / viewmodel 等源文件

设计的目标：把「spec 要求什么」和「代码现在实现到什么程度」对齐，列出**逻辑层**该测哪些点、
每个点怎么测、预期结果是什么。设计阶段**不写测试代码**，只产出这份表。

> **API/隔离手段拿不准时**：若不确定某个 hypium 能力（断言/Mock/匹配器）是否支持、能否覆盖某测试点，
> 查 `references/api/hypium.md`（@ohos/hypium 官方单测 API 原文），别凭空臆测能不能测。

---

## 只测逻辑层（unit）

本 skill 只覆盖**逻辑层**（纯函数 / service / viewmodel / 持久化），不测 UI（页面渲染、控件、
导航、点击交互）。判断一条 AC 是否属于逻辑层：

| 归逻辑层（要设计） | 归 UI 层（跳过，本 skill 不管） |
|---|---|
| 计算、格式化、排序、过滤、分组、判断 | 点击、输入、滑动、长按、聚焦 |
| 保存 / 重启后保持 / 写 DB / 更新记录 | 显示、出现、消失、高亮、置灰、跳转、返回 |
| 内部方法调用链、状态字段变化（非视觉） | 空状态提示、占位图等纯视觉反馈 |

一条 AC 若同时含逻辑和 UI（如「过滤后显示空态」），只取其逻辑部分（过滤结果），UI 部分跳过。

## 文件模版（复制后填写）

```markdown
# F{编号} 测试设计：{功能名}

> Spec 来源：spec/baseline/features/F{编号}_{xxx}.md
> 相关源码：entry/src/main/ets/services/XxxService.ets, models/Xxx.ets …（列出读过的关键文件）

## 测试点清单

| 用例ID | 追溯AC | 类别 | 测试意图 | 前置/输入 | 预期结果 | 依赖与隔离 | 当前实装 |
|--------|--------|------|---------|----------|---------|-----------|---------|
| F{编号}_AC01_match | AC1 实时过滤 | 正常 | filterMedia 按文件名命中 | media=[a.jpg,b.png], q='a' | 返回 [a.jpg] | 纯函数 | 已实现→GREEN |
| F{编号}_AC01_empty_query | AC1 实时过滤 | 边界 | 空查询返回全部 | media=[…], q='' | 原样返回全部 | 纯函数 | 已实现→GREEN |
| F{编号}_AC01_null_media | AC1 实时过滤 | 异常 | media 为 null 不崩 | media=null, q='a' | 返回 [] 或抛明确错误 | 纯函数 | 部分→RED |
| F{编号}_AC03_persist | AC3 重启后保持 | 正常 | 收藏写入 DB | 收藏 item1 | DB 中 item1.isFavorite=true | RDB，构造器注入 fakeDb | 部分→RED |

## 备注

- **三类输入**：AC1 已按「正常(命中) / 边界(空查询) / 异常(null)」拆成 3 行；每个被测函数都要覆盖三类。
- **隔离方案**：F{编号}_AC03 依赖 RDB，源码 XxxService 已支持构造器注入 → 测试注入 fakeDb，断言写入参数。
- **预期 RED 说明**：F{编号}_AC03 当前 `persist()` 只 `console.info` 未写库 → 用例预期 RED，实装补完转 GREEN。
- **spec↔代码冲突**（如有）：按 spec 写预期并标注，例如「⚠️ F{编号}_AC02：spec 要求结果去重，代码未去重 → 预期按 spec(去重)，当前预期 RED」。
```

## 字段说明

| 列 | 填法 |
|---|---|
| **用例ID** | `F{编号}_AC{序号}_{行为}`，全局唯一、跨轮稳定。一条 AC 多个边界 → 多个 ID。 |
| **追溯AC** | 对应 spec `## 验收标准` 里的哪一条（写 AC 序号 + 短描述），保证每个用例可回溯（标准 1）。 |
| **类别** | `正常` / `边界` / `异常`（标准 2）。每个被测函数三类都要有，便于核对覆盖是否完整。 |
| **测试意图** | 一句话说清这个用例验证什么行为。 |
| **前置/输入** | 构造的输入数据、前置状态。尽量最小化（≤10 条数据覆盖所有边界）。 |
| **预期结果** | 期望的返回值 / 副作用 / 状态变化，必须是**可断言**的具体值，不能写「正常工作」。 |
| **依赖与隔离** | 外部依赖（DB/fileIo/http/Context/photoAccessHelper）+ 隔离方式（见下）。无依赖填「纯函数」。 |
| **当前实装** | 读源码判断：`已实现→GREEN` / `未实现→RED` / `部分→RED`。决定用例预期是绿还是红。 |

### 隔离方式选型（依赖与隔离列）

```
方法是否依赖外部服务（DB / fileIo / photoAccessHelper / http / Context）？
├─ 否 → 纯函数：构造输入 → 调方法 → 断言返回值
└─ 是 → 按优先级选隔离方式（具体写法见 test-case-template.md）：
        1. 构造器注入   —— 源码已支持依赖注入，测试传 fake 实现（首选）
        2. 暴露静态实例 —— 源码是 `private static repo/api`：标注「暴露为 static 后 mock 实例方法」
                          （ArkTS 禁 `.prototype`，必须走可达实例；这是 service↔repo 类的常见情形）
        3. Wrapper 函数 —— 源码固化用 @kit.*，包一层用户态函数后 mock
        4. 真实 Context+RDB —— 用 @kit.TestKit 拿真实 UIAbilityContext；若碰 RDB，beforeAll 同时 init Prefs+Rdb（兜底）
```

> 设计阶段只需在「依赖与隔离」列写明选哪种方式 + 理由；具体代码留给第二步。

## 覆盖与拆分（最高标准 2 / 6）

- **三类输入全覆盖（标准 2）**：每个被测函数都要有「正常 + 边界 + 异常/错误」三类用例，不能只有
  happy path。边界至少考虑：空值、零、最大/最小、越界、null/undefined、类型边界。
- **一条 AC ≥ 一个用例**：同一 AC 涉及多种边界时，**每种边界单独一行**（命名带边界描述），不合并成
  「一个用例多次断言」——报告才能精确定位是哪种边界挂了。
- **最小且无冗余（标准 6）**：用最少用例覆盖最多不同行为，合并等价输入，不重复断言同一逻辑。

## spec 与代码冲突（最高标准 3）

读源码时若发现**代码行为与 spec 不一致**：「预期结果」一律**以 spec 为准**（测试会 RED，从而暴露代码
bug），并在「备注」标注 `⚠️ spec↔代码冲突：<差异>`。**不要**按代码现状写预期——那只会把 bug 固化成
「通过」。

## 当前实装判断（读源码）

| 源码形态 | 判定 | 用例预期 |
|---|---|---|
| 有实质逻辑（如 `return this.deletedTimestamp > 0`） | 已实现 | GREEN |
| 只有 `console.info` / 空方法体 / `throw new Error('Not implemented')` | 未实现 | RED |
| 部分实现（内存改了但没写库） | 部分 | 已实现部分 GREEN + 缺失部分 RED |

> 设计阶段标 RED 是 TDD 的正常信号，表示「spec 要求但代码还没做」，不是错误。

## 映射 / 解析 / 占位 用例的设计要点（踩坑总结）

这几类最容易设计成「跑得过但验不到真东西」，逐条对照：

- **`fromJSON`/映射类必须用「真实外部 JSON 形状」做输入**，不能用 model 自己的字段名。model 的
  `fromJSON` 是与后端的契约边界；若喂 model 内部驼峰字段（如 `userId`/`authorName`/`read`），测试会和
  「字段名映射 bug」自洽、永远抓不到。设计时**对照真实接口/源码确认 wire 字段**（如 WP REST 的
  `ID`/`author.name`/`unread`），按真实形状构造输入，「预期结果」写映射后的目标字段值。**尤其警惕反向
  语义字段**（如 `unread` ↔ `read`：默认值若选错，缺失字段会被解析成相反含义）。

- **解析/列表类「预期结果」必须是字段级具体值，不能只断条数**（标准 5 的强化）。`返回 length=2` 测不出
  映射对不对——同样的 length 下字段全错也过。至少对其中一项断关键字段的具体值。

- **占位 / mock 数据源不算「已实现」**：若焦点函数当前返回内置 mock 常量 / `PH-*` 占位（返回写死列表、
  仅 `emit` 不发请求、`return false` 等），「当前实装」标 **RED**，且「预期结果」写 **spec 期望的真实
  行为**（会 RED，实装后转 GREEN）。**绝不要**把 mock 常量的条数/内容当成预期值——那是假绿（测的是
  常量不是实现）。

- **会被 skip 的用例不得标 GREEN**：若某测试点的隔离手段在 ArkTS 下不可行而预计会被跳过（如只能 `.prototype`
  打桩），「当前实装」不能写「已实现→GREEN」，否则报告高估实现率；改用「暴露静态实例」隔离方式（见上），
  或标注「需暴露实例后方可验证」。

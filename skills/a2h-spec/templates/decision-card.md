# 决策卡：向用户提问的唯一格式

## 铁律

**任何向用户提出的问题都必须是选项题，不能是填空题。**

用户回复一个编号即可推进。理由：填空题要求用户当场设计方案，而用户手上没有你刚读过的源码上下文；
选项题把「读源码、列可行解、评估影响」留在本侧，把「哪个更符合项目意图」交给用户——这才是各自
真正擅长的部分。

违反此格式的提问形态（禁止）：

- 「你希望会员校验放在哪一层？」——开放式，用户得替你设计
- 「请提供 XXX 的取值」——模型能从源码读出来的，不要问
- 「是否继续？」——没有给出继续与否的后果差异
- 「有什么想法吗？」——把决策成本整个推给用户

## 格式


规则：

1. **2–4 个具体选项**，外加 `[N] 其他（请说明）`。选项数超过 4 说明问题该先拆分。
2. **恰好一个标 ← 推荐**，并给一句话理由。没有推荐项 = 本侧没做完功课。
3. 每个非推荐项写明**代价或副作用**，不是只写名字。
4. 写明**影响面**（哪些 requirement ID）与**不选的代价**。
5. 用户回复后，写回 `spec/decision-ledger.md`：`D-014 = [1]（ArkTS 侧复刻同一 VM 基类）`，
   并在受影响 AC 的 `真:` 锚写 `真:decision:D-014`。决策必须可回放。

## Gate 审批固定四选项

Gate A / Gate B / Gate C 一律使用同一组选项，用户不必每次重新理解格式：

````markdown
## Gate C：功能 Spec 完成，请审批

<摘要：功能数 / 需求数 / 阻断项 / 建议项 / 关键决策，见 gate-summaries.md>

[1] 通过，进入下一阶段
[2] 通过，并把下列建议项记为例外（请列编号；将写入 decision-ledger 并附关闭条件）
[3] 先修下列问题再来（请列编号）
[4] 中止本轮

回复编号即可；选 [2]/[3] 时附上要处理的条目编号。
````

- 存在 🔴 阻断项时，`[1]` 不可选——摘要须直接说明「本次不可选 [1]，因为有 N 条阻断项」。
- `[2]` 的每一条例外都必须落到 decision-ledger，带原因与关闭条件；没有关闭条件的例外不成立。

## 阻塞上报（下游阶段用）

当某阶段无法推进，且**责任归属无法机械判定**时（典型：AC 按当前描述实现不了——
可能是 Spec 写错、Plan 切分错、或 Execute 没找到办法），用决策卡上报，由用户指定 owner：


选项与 owner 的对应关系写死，避免推诿：`[1]→owner_stage=spec`、`[2]→plan`、
`[3]→当前阶段记 deferred`。用户选定后写入 `open-findings.json` 对应条目的 `decision_ref`。

## 连续未收敛时强制升级

`open-findings.json` 中同一 `finding_key` 连续出现 3 轮（`escalate: true`）时，**禁止再自动重试**，
必须出决策卡：

````markdown
## 阻塞 B-007：F003-AC08 已连续 3 轮未通过

[1] 换实现路径（说明拟采用的新路径）　← **推荐**
[2] 判定为平台差异，走 HARD-DIV 决策改写该 AC
[3] 记为 deferred，写明关闭条件
[4] 中止该 feature，转人工处理
````

这条规则的目的是止损：同一症状修到第 3 轮还不过，通常说明方案错了而不是改得不够，
继续叠补丁只会让实现路径越来越多。
